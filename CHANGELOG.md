# Changelog

All notable changes to Whereabouts are recorded here. The format follows [Keep a Changelog](https://keepachangelog.com/en/1.1.0/), and versions follow [Semantic Versioning](https://semver.org/).

## [Unreleased]

### Changed

- **A living background.** The background is now a slowly turning globe drawn in characters. Countries your apps have an open connection to glow, and when an app connects somewhere new, that country flashes (amber for trackers). A connection counts as new if it was not listed in the last 10 minutes; for a minute and a half after the service starts, nothing flashes while it re-lists connections that were open all along. It uses only what the app already shows: nothing new is collected or sent, and nothing flashes that did not happen. Moving the mouse stirs the characters, a click on the background sends a wave, and you can drag the globe to spin it. There is no "you are here" marker: Whereabouts does not know or guess where you are.
- **Lighter on your computer.** While the window is minimised, the background and every other animation stop (Windows' web view kept drawing before); at rest the globe draws slowly, and the "Watching" dot pulses a few times when the app opens instead of forever. Measured on an installed test build with live traffic: just under a third of one processor core with the window open (flashes and mouse movement included) and about 2% minimised, down from about one core either way in 0.2.0. With Windows' "Animation effects" turned off, it stays still and changes only when your connections do.
- CI runs the UI's own tests (Node's built-in test runner; no new packages).
- **For developers: a detection lab** (`lab/`, never shipped, never real user data). Scripted sessions of real apps, started logged out, are recorded on GitHub's disposable Windows runners, stitched into simulated user-weeks with staged problems and replayed through the shipped detection code, which moved into the `whereabouts-detect` crate (no change in behaviour). It reports false alarms per user-week, detection rate and time to detect. `whereabouts-service --status --json` prints the status for scripts.

### Security

- **Only the Whereabouts app, or a command line run as administrator, can change your blocks.** Any program could run Whereabouts' command line to pause blocking or remove a rule without asking you, so a blocked app could unblock itself. The same goes for deleting history, silencing alerts and list-update settings. Reading (`--status`, `--rules`) still works without administrator rights.
- **Programs that share a name are no longer merged.** The Apps screen grouped connections by file name, so a program called `chrome.exe` in any folder appeared inside real Chrome's card, with Google's name and "signed" badge. Each program file now has its own card, and programs with the same name show their folder.
- **The service takes its connection to the app back.** While Whereabouts' service was stopped (during an update, or after a crash), any program could take the name of its private connection to the app, and the service then could not answer the app until it restarted. It now keeps trying, and answers as soon as the name is free.
- **Warnings that cannot be undone default to Cancel.** In "Delete everything Whereabouts saved?" and "Stop these warnings?", pressing Enter deleted everything or silenced the warning; Cancel is now the default button.

### Fixed

- **"Undo" no longer removes a block you already had.** Blocking something that was already blocked showed "Blocked · Undo", and Undo removed the original rule. It now says it was already blocked. The Block menu no longer offers to block an app that is already blocked.
- **The Block menu opens in view on every screen.** Opened from a long list of connections, it appeared far down the page, so "Block…" seemed to do nothing.
- **A blocked app is now cut off both ways.** Blocking an app stopped only the connections it made, so a blocked torrent client could still trade with peers that connected to it (Windows Firewall usually lets them in). Incoming connections are now refused too, except from this computer itself, so the app's own window keeps working. Apps you already blocked get this when the service starts.
- **Blocked apps no longer show web pages from the internet, ads included.** Apps such as uTorrent Web show web pages in their window through Microsoft Edge WebView2, a part of Windows shared by many apps, which fetched them even while the app was blocked. Blocking an app now also sets WebView2's per-app setting for it so those pages cannot load, from the next time the app starts; the app's own local pages keep working. Unblocking, pausing and uninstalling remove the setting again. The setting is keyed by file name, so another program with the same file name also loses pages shown through WebView2.
- The frosted-glass cards now blur what is behind them. A screen's fade-in animation stayed in effect after it ended, which switched the blur off for every card on that screen. Switching screens also showed the cards unblurred for half a second while the screen faded in; the cards are now frosted from the first frame and only their contents fade in.

## [0.2.0] - 2026-11-20

*Control.* Whereabouts can now block apps, sites and addresses, warn you, and keep its lists current.

### Added

- **Blocking.** **Block…** on every connection blocks that site for that app, that site for every app (with a warning), that address, or the whole app; app pages have **Block app**. Windows shows exactly what will be blocked and asks you to confirm; a note offers **Undo**. The **Rules** screen lists what is blocked, for which app and since when, with **Unblock** and **Pause all blocks / Resume**; a banner shows on every screen while blocking is paused.
  - Blocks are rules in the Windows Filtering Platform under Whereabouts' own name. They stay in force across restarts and while the app is closed, are saved in the encrypted database and re-applied when the service starts, and are kept when updating. Uninstalling removes every block.
  - A site is blocked by the addresses the Windows DNS service confirms for it (and for names that point to it); learned addresses expire a day after they were last seen. A block for every app never blocks addresses that other, unblocked sites also use.
  - Whereabouts never blocks core Windows programs, Microsoft Defender, itself, DNS servers, loopback or your local network; core Windows networking programs are always exempt from its blocks.
  - Command line: `--rules`, `--block-app`, `--block-domain`, `--block-ip`, `--for`, `--unblock`, `--pause-blocking`, `--resume-blocking`, and the emergency switch `--unblock-all` (works even if the service is not running).
- **Alerts.** A new **Alerts** screen with reasons and actions (Block…, Dismiss, This is fine): tracker contacts (EasyPrivacy; one per app and tracker a day), connections to networks on **Spamhaus' DROP** list (high), and signs that something is hiding from Whereabouts (fake DNS events, untraceable traffic). "This is fine" stops alerts for that app and tracker or network (for a risky network, Windows asks first); Dismiss only clears an alert.
- **Tray and notifications.** The app can start in the tray when you sign in (asked once, suggested on; only the installed app). Windows notifications tell you when an app uses the internet for the first time (after a quiet first day), when Whereabouts stops watching and when it is back, when blocking stays paused for an hour, about alerts (at most one per app an hour), and once a day about tracker contacts. **Notifications name no apps or sites unless you allow it.**
- **List updates.** Downloads nothing until you answer the app's question (both switches suggested on; change them on the Privacy screen):
  - Whereabouts' tracker, company, country and network lists from its GitHub releases, checked daily, **signed with Ed25519** and refused if the signature, any file or its sequence is wrong; swapped in whole.
  - Spamhaus' DROP list from spamhaus.org at most once a day (Spamhaus does not allow it to be passed on, so each computer fetches it itself). Turning it off deletes it.
  - HTTPS only, through Windows' own TLS and certificate store. A weekly workflow builds and signs the data.
- **Better names.** Trackers hidden behind a site's own name ("CNAME cloaking") are recognised for labels, alerts and blocks; connections show "via …" when that revealed who is behind them. Whereabouts reads Windows' DNS cache (cache only, never the network) at start and when a site block is added, so sites looked up earlier get names and blocks.
- Live connections carry the program's full path (shown on app pages).

### Changed

- The database moves to schema version 4 (blocking rules, settings, known apps, alerts). A 0.1 database is upgraded in place and keeps its history; apps already in your history count as known.
- New pipe requests for rules, notices, alerts and list updates; `Status` reports blocking, the DROP list and list updates.
- CI: the live job (capture, firewall and end-to-end blocking tests, and reading the DNS cache) is now a required check.

### Security

- The service accepts program paths only on this computer's own drives and refuses links or `..` along them, before touching the file system, so it never connects to another computer as SYSTEM.
- Native Windows confirmations for blocking and for silencing risky-network alerts, so the app's web view cannot do either on its own; confirmations show the full program path and cannot be spoofed with control characters.
- "This is fine" needs a known program path; serious alerts can never be pushed out of the list by many tracker alerts.

## [0.1.1] - 2026-11-17

### Fixed

- The Privacy screen's count of Whereabouts' own internet connections now includes the Microsoft WebView2 helper processes that draw the app's window (they run as separate programs, so matching by name missed them), and identifies the app and service by process ID rather than by file name. Checked on 0.1.0: these helpers made no internet connections.

## [0.1.0] - 2026-11-16

First release: a developer preview for Windows 10 (22H2) and 11, 64-bit.

### Changed

- `serde_with` (used inside Tauri) updated from 3.17 to 3.24, fixing a crash on empty sequences in its `KeyValueMap` (GHSA-7gcf-g7xr-8hxj).
- PRIVACY.md now describes exactly what version 0.1 does: it makes no internet requests at all (the installer may fetch Microsoft's WebView2 if Windows lacks it), and features that are designed but not built yet (on-device learning, retention and browser settings, foreground tracking, signed update downloads) are listed separately as planned. SECURITY.md lists 0.1.x as supported.
- Minimum Rust version raised from 1.85 to 1.88, to take security fixes for `time` (RUSTSEC-2026-0009) and `quick-xml` (RUSTSEC-2026-0194, RUSTSEC-2026-0195), both reached through Tauri. Six unmaintained (not vulnerable) crates inside Tauri are recorded in `deny.toml` with reasons; any new advisory still fails CI.

### Added

- **Export to CSV** and **Delete everything** on the app's Privacy screen. The export is streamed from the service in pages and written by the app to a place you choose in a Windows Save dialog; deleting asks for confirmation in a Windows dialog, is carried out by the engine (which also forgets finished connections still waiting to be saved, so nothing from before reappears), and keeps recording new connections afterwards. New pipe requests `ExportPage` and `DeleteAll` (the latter only with an exact confirmation phrase).
- Installer (M7): `scripts/build-release.ps1` builds `Whereabouts_<version>_x64-setup.exe` (NSIS, for all users) with the app, the background service and the offline data, plus `SHA256SUMS.txt`. The installer only installs to `C:\Program Files\Whereabouts` (the service only trusts programs there), stops and removes an older version's service before replacing its files, registers and starts the service afterwards, and on uninstall stops and removes it and asks whether to delete the saved history (default: keep). New service commands for this: `--register` (only from the installation folder) and `--unregister [--delete-data]`.
- Release workflow: for every pull request that touches the installer, GitHub builds it on a fresh Windows machine, installs it silently, checks the service (running, automatic, LocalSystem, sees traffic, saves history), uninstalls it and checks it is gone and the history kept. A `v*` tag also creates a draft release with the installer and checksums.
- Desktop app (M6, `ui/`): a Tauri v2 app with a Svelte 5 + TypeScript UI in a "night chart" design: ink navy, frosted glass, a signal-teal accent, and a backdrop of coordinate grid, contour lines and routes from this PC to destinations. **Overview** (live status and health checks, an activity graph, apps, destinations, countries, data sent and received, top apps, companies and countries, the biggest connections), **Apps** (per-app publisher and signature, sent and received, destinations, countries, trackers, and where it connects), **Connections** (search and filters for trackers, unverified names and unsigned apps) and **Privacy** (what is kept and never read, retention, where data lives, and Whereabouts' own internet connections, measured). Trust levels are shown as labelled badges. Everything is bundled: no web fonts, CDNs or remote images, enforced by a strict content security policy; the web view can call only two read-only commands. In an ordinary browser the UI runs on clearly marked demo data, for design work.
- The "kernel events cannot be faked" check is repeated by the app and `--status` from the user's own account. The installed service runs as SYSTEM, which Windows allows to register the kernel providers' IDs, so its own check raised a false alarm; ordinary programs are still refused.
- `whereabouts-client` crate: connecting to the service and the peer checks, shared by `--status` and the app. The service now also answers programs installed next to it in `%ProgramFiles%\Whereabouts` (compared by folder ID), so the app can connect; `--install` copies the app when it was built next to the service.
- Windows service (M5b): `--install` copies Whereabouts and its offline data to `%ProgramFiles%\Whereabouts` and registers and starts the **Whereabouts** service (LocalSystem, starts with Windows, restarts after a failure); `--uninstall` stops and removes it, keeping saved data unless `--delete-data` is given. The installing user may use the service's pipe. The service saves its last flows when stopped or when Windows shuts down, and logs its own warnings (never captured data) to `service.log` in the protected data folder. `--console` refuses to start while the service runs. Clients trust the installed service by its process ID from the Service Control Manager, since normal users cannot inspect a SYSTEM process. The database key is now protected with DPAPI for this computer rather than one account, so the service and administrators' commands share it; an older key is moved over once. The live test has an opt-in `-Service` stage that installs, checks and removes the service.
- Pipe hardening after review: the account running Whereabouts may only read and write data on the pipe, no longer create instances of it (generic write includes that right for pipes, which would have let its other programs add instances to receive clients). The peer check now opens the other process first and checks it only through that handle, rejects a process that started after the connection (a reused process ID), and locks and re-confirms its running file before comparing it with our own.
- Local channel between the service and its clients (M5a): a named pipe (`\\.\pipe\Whereabouts`, new `win-pipe` crate) that only SYSTEM, Administrators and the account running Whereabouts can open, never from the network. The service creates it as the first instance (so a program that took the name first makes it fail rather than be shared) and both ends check that the program on the other end runs the same file as their own (by file ID); clients connect at the anonymous level so they cannot be impersonated. Messages are typed and versioned (`ipc` crate): length-prefixed JSON up to 1 MiB, unknown types and fields refused, limits clamped. `--console` now serves the pipe, and the new `--status` command asks it for its counters, top flows and top apps; the live test runs it as administrator and as a normal user. Trust levels (unconfirmed publisher, app-reported or guessed domain) are separate fields, so shortening text cannot drop them.
- App and publisher names are made safe to show: control characters and invisible Unicode formatting characters (such as right-to-left overrides) are replaced with `?`, so a program cannot rewrite the terminal or disguise its name.
- Encrypted storage (M4): finished flows are saved to an SQLCipher database (whole file encrypted with a random 256-bit key) in `%ProgramData%\Whereabouts`, a folder created already restricted to SYSTEM and Administrators; an existing folder or file is refused if it is a link/junction or owned by another account (ordinary users can pre-create folders in `%ProgramData%`). The key is stored only DPAPI-encrypted for the account running Whereabouts (new `win-secrets` crate). Deleted data is overwritten. Flows are kept 30 days, then folded into hourly totals kept 180 days. For web browsers, only the registrable domain is stored (decision D5). New commands: `--history` (top apps of the last 24 hours), `--export <FILE>` (CSV, with spreadsheet formulas neutralised) and `--delete-all --yes`. The live test checks that the database file contains no readable app names or domains and that the folder is restricted.
- Offline company and country lookups (M2), in the `enrich` crate: registrable domains (Public Suffix List), tracker domains (EasyPrivacy's whole-domain rules), the company and kind of service behind well-known tracking, analytics, attribution, messaging and diagnostics domains (Whereabouts' own `data/companies.tsv`), and the country and network owner of IP addresses (DB-IP Lite). Nothing is looked up online. `scripts/update-data.ps1` downloads the third-party files at build time (not committed) and records their versions and hashes. The console shows OWNER and CC columns; a domain only the app itself reported (`?`) never supplies the company. Non-commercial lists (Disconnect, DuckDuckGo Tracker Radar, Ghostery) were rejected for licence reasons.
- App identity checks the file a process is **actually running**: at its first network activity, Whereabouts takes the image path from the kernel's own record (which follows the file even if the program renamed itself after starting, and which the program cannot edit), locks that file, asks the kernel again and requires the exact same path and the same file (volume and file ID) to confirm it is still the running image, and hands the locked handle to the background check. A program can no longer borrow a publisher by renaming its own file and putting a signed one at its old path. When the running file cannot be confirmed (for example, the process had already exited), the file at its start path is checked and the publisher is shown with a `?`.
- App identity (M3): for every app that uses the network, Whereabouts checks the program file's code signature (embedded Authenticode or a Windows security catalog, so renamed copies of signed programs are still recognised and modified copies are not), its SHA-256 hash, and its Microsoft Store package. Each check opens the file once with sharing that blocks writes, renames and deletes, and hashes and verifies through that single handle; every process is checked on its own, and signature results are cached only by content hash, so a program file swapped at the same path never inherits the original's result. Checks run on a background thread, **without any network access** (no revocation checks, no certificate downloads), which a live test verifies. Kernel `\Device\HarddiskVolumeN\...` paths are mapped to drive letters. The console shows a PUBLISHER column (`UNSIGNED` / `INVALID SIGNATURE` when relevant).
- Protection against faked kernel events (S1): research showed Windows refuses to let programs register the `Microsoft-Windows-Kernel-Network` and `Microsoft-Windows-Kernel-Process` provider IDs (`EventRegister` fails with "access denied", even as administrator), so their events cannot be faked from user mode, unlike the DNS Client provider. `win-capture::protection` checks this at start-up and the console warns if a Windows version ever allows it; a test that needs no administrator rights checks it on every CI run, including Windows Server. `examples/forgery_probe.rs` is the research tool.
- DNS confirmations are kept per name, with a timestamp for every name/address pair, and an app's lookup is checked against them when it arrives, with the result stored alongside it. Guessed (`*`) labels are given only when exactly one name currently points at an address, so extra names make the guess disappear rather than steering it. An attacker who points their own domain at a popular address can no longer verify a different name or, by flooding lookups, undo an earlier verification; names and addresses expire individually, and full lists drop their stalest entry. "Verified" now explicitly means the Windows DNS service resolved that name to that address, not that the server belongs to whoever the name suggests.
- DNS label trust: labels are now **verified** (the app's lookup matches what the Windows DNS service itself resolved), **unverified** (only the app reported it; shown with `?`), or **inferred** (from another app's verified lookup; shown with `*`). The DNS service's own events (3020) are accepted only from the real service process (looked up via the Service Control Manager), because any program can write events under the DNS provider's ID; forged events are counted as `rejected` and the console warns about them. Inferred labels come only from verified answers, so one app can no longer plant labels on another's connections, and the table of verified answers evicts the oldest entries when full.
- DNS names are limited to characters legal in DNS (ASCII letters, digits, `-`, `_`, `.`), which blocks bidi, invisible and look-alike Unicode characters.
- Domain names for connections (M1): `win-capture` reads "DNS query completed" events from the `Microsoft-Windows-DNS-Client` ETW provider, which are logged in the app that asked (also for cached answers). `core::dns::DnsMap` remembers each process's answers (bounded per process and in total, 30-minute lifetime, cleared when a process exits) and labels its flows. Connections to an address that only another app looked up get an *inferred* label. DNS names are validated (length, no control characters) before use. The console shows a DOMAIN column.
- `win-capture`: live network capture from the `Microsoft-Windows-Kernel-Network` ETW provider (TCP and UDP, IPv4 and IPv6), with bounded queues and counters for dropped and unreadable events. Event decoding is verified against real Windows 11 events and covered by unit tests.
- `win-capture`: executable path lookup for a process ID, plus process start/exit events from `Microsoft-Windows-Kernel-Process`, so flows and names are closed when a process exits and a reused process ID is never mixed up with the old process. Process events are never dropped (network events may be, and are counted), and a process is identified by its ID and start time.
- `core`: `NetEvent` model and `FlowTable`, which aggregates events into per-app, per-destination flows and ignores loopback traffic. Memory is capped per process and in total; traffic beyond a process's limit goes into a visible "many destinations" flow for that process, so one process cannot hide another's traffic by flooding the table. Overflow flows are capped too, with one shared bucket beyond the cap.
- `service`: `--console` mode showing live flows per app (run as administrator).
- `win-capture`: `etw_probe` example for inspecting raw ETW events during development.
- Live ETW integration tests (`crates/win-capture/tests/live_capture.rs`), skipped by default, plus `scripts/live-test.ps1`, which runs them and a console smoke test with one UAC prompt, and a CI job that runs them on GitHub's Windows runners.
- Design specification (`docs/design-spec.md`), privacy policy, security policy and contribution guide.
- Cargo workspace with `core`, `enrich`, `ipc`, `store`, `win-capture`, `win-firewall` and `service` crates.
- `core`: connection metadata model, robust statistics (median, MAD, robust z-score) and domain entropy.
- CI on Windows: formatting, Clippy, tests, and licence/advisory checks with `cargo-deny`.
