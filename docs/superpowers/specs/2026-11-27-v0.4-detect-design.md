# Whereabouts v0.4 "Detect": design

Date: 2026-11-27. Status: approved 2026-11-27.
Builds on v0.3 ("Learn", `2026-11-24-v0.3-learn-design.md`) and `docs/design-spec.md` §6.2, §6.6.

## 1. Intent

v0.3 warns when a known app changes its behaviour, but two holes remain:

1. **New programs get a free week.** A program seen for the first time is "learning" for 7 days and raises no behaviour warnings. A renamed copy (the lab's `curl.exe` saved as `Discord.exe` in a user folder) is a new path, so it slips through: the lab caught 0 % of these.
2. **Beaconing is built but off.** Malware often "checks in" with its server on a steady timer. Layer 2 has the detector, but the lab couldn't measure its false alarms (30-minute sessions hide the 5–15-minute check-ins ordinary apps make), so it ships off.

v0.4 closes both, under the same release bar as v0.3. The roadmap's Isolation Forest (Layer 3) is **not** in v0.4: the user chose to close these gaps first, because Layer 2 already catches most staged problems and Layer 3 couldn't be trained or measured with today's lab.

**Success:** the impostor check catches the lab's renamed-program test without adding false alarms; beaconing is switched on only if the lab shows it keeps the bar.

## 2. Goals, non-goals, anti-goals

**Goals**
1. **Impostor warning:** when a program goes online for the first time and another program **with the same file name** is already known **in a different folder**, and the new one is **unsigned or signed by a different publisher**, raise a high-severity behaviour alert at once, without waiting for learning.
2. **Beaconing decision:** a lab option for multi-hour sessions; measure beaconing's false alarms; switch it on (in `Toggles::default`) only if the shipped set still passes the release bar.

**Non-goals**
- Layer 3 / Isolation Forest (stays on the roadmap; later).
- Warning about every new unsigned program (rejected by the user: too noisy for portable tools and dev builds).
- A built-in list of popular apps and publishers (approach B, rejected).
- Changing the 7-day learning period.

**Anti-goals**
- Warning when the user simply has two real installs of the same app from the same publisher (e.g. Discord and Discord PTB).
- Any new stored data about the user (the check uses what profiles already keep).
- Turning beaconing on without lab evidence.

## 3. Decisions made with the user (2026-11-27)

| # | Decision | Reason |
|---|---|---|
| D1 | v0.4 closes v0.3's gaps (option B), not Layer 3 | Layer 2 already catches most problems; Layer 3 can't be trained in today's lab and would rarely help most users |
| D2 | New programs: warn only about **impostors** (same name, different folder, not the same signer) | Almost never innocent, so quiet; catches the renamed-program trick |
| D3 | Impostors are found by comparing with this PC's own profiles (approach A) | No new data, no list to maintain; approach B (built-in app list) adds upkeep and noise; approach C (names only) can't tell real from fake |
| D4 | Beaconing goes on only if the lab, with long sessions, shows the shipped set still passes the release bar | Same rule as v0.3 (U4/U8) |

## 4. The impostor check

**When:** the first time the Learner creates a profile for a program path (its first finished connection, or first traffic) — after the backfill gate, like all live learning.

**Rule:** look up the saved profiles (`Store::profile_rows`) for any other profile whose **program file name** (from its path, case-insensitive) equals the new program's file name and whose **path differs**. Raise an impostor warning when, for at least one such profile:
- that profile's stored signer (`last_publisher`) is set, **and**
- that profile is **established**: past its own 7-day learning period (*builder-check call:* installers and one-off tools named `setup.exe`, `update.exe` and the like run briefly and never become established, so a vendor's signed `setup.exe` can't make every other `setup.exe` look like an impostor), **and**
- the new program is unsigned, its signature is invalid, or its signer differs (case-insensitive).

No warning when the new program's signature couldn't be checked (`Signature::Unknown`): skip, as v0.3 does for "binary changed". *Builder-check call:* `AppFacts` gains a `signature_checked: bool` (false for `Unknown`), set by the service and the lab replay, so "unsigned/invalid" and "couldn't check" are told apart. No warning when no other profile has the name, or when every match has no stored signer (two unsigned copies: nothing to compare).

**Toggle:** `Signal::Impostor` has a toggle like the other signals, **on** by default and in the lab's shipped set (*builder-check call*). If the lab shows it alone pushes false alarms over the bar, it ships off (U4), as for any signal.

**The alert:** a behaviour alert with a new reason `Signal::Impostor` (store spelling `impostor`), severity **high**, notified, raised even while the new program is still learning. `value` = the other (known) program's path; the alert's `app_path` is the new program. Plain sentence in the app: "Same name as {known program path}, but {not signed | signed by someone else}. It may be pretending to be that program." It combines with other reasons in the usual 10-minute window.

**This is fine:** saves a lasting allow for the new program's path (`behaviour|{new key}|impostor|{known path}`), so it doesn't warn again. Block app / Dismiss work as for other alerts. Reset removes that allow, like other behaviour allows.

**Lab:** the existing `renamed_binary` scenario (curl.exe renamed Discord.exe in a user folder, where the real Discord is signed by Discord Inc.) is exactly this case. The bar's fitting rule for `renamed_binary` becomes: an `impostor` reason (today it is "any medium+").

**Privacy:** nothing new is stored; the check reads profile paths and signers that are already disclosed in PRIVACY.md.

## 5. Beaconing decision

- **Lab sessions:** let `lab.yml` run sessions long enough for 5–15-minute check-ins to repeat at least 6 times: **180-minute sessions** (fits the 340-minute job cap with setup). Default stays short for weekly runs; the long run is started by hand.
- **Measure:** a development run, then a fresh held-out run with nothing tuned on it (as in v0.3). Report beaconing's false alarms per user-week alone and the shipped set with beaconing on.
- **Decide:** if the shipped set **with beaconing on** passes the bar (≤ 1.0 medium+ false alarm per user-week and ≥ 50 % in ≥ 3 of 5 types), beaconing goes on in `Toggles::default`. Otherwise it stays off and the reason goes in the release notes. Its thresholds (6 connections, CV ≤ 0.1, 10 s–1 h gaps, ≤ 64 KB each) may be tuned on the development run only.
- Lab connection lines still carry no bytes (known gap, disclosed); a beaconing "This is fine" already saves a lasting allow per app and destination.
- **Release gating** (*builder-check call*): 0.4.0 is released after the long held-out run, which measures both changes. Whatever it says about beaconing, the impostor check ships (if it keeps the bar); beaconing goes on only if the shipped set with it passes, otherwise it stays off and the release notes say why. The runs are started from the controller session with `gh workflow run`, like v0.3's.

## 6. What changes, roughly

- `crates/store`: `Signal::Impostor` (+ spelling); nothing else.
- `crates/detect`: the impostor check in the Learner's new-profile path; `severity_of(Impostor) = High`; reason allow key; `AppFacts.signature_checked`.
- `service`, `crates/lab-replay`: set `signature_checked` (false for `Signature::Unknown` / no signature data).
- `ui`: the sentence for `impostor` in `reasons.ts` (+ test), demo alert.
- `lab`: long-session option; `renamed_binary` fitting rule = `impostor`; `SIGNAL_SEVERITY`/shipped set mirror.
- Docs: design spec §6.2 notes, PRIVACY.md unchanged (no new data), CHANGELOG, release notes 0.4.0.
