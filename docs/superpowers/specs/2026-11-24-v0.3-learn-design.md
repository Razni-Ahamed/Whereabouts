# Whereabouts v0.3 "Learn": design

Date: 2026-11-24. Status: approved 2026-11-24.
Builds on `docs/design-spec.md` §6.2 (Layer 2), §6.4 (alert scoring), §6.5 (feedback), §6.6 (lab).
Where this document and the spec disagree, this document wins for v0.3, and the spec is updated to match.

## 1. Intent

Whereabouts v0.2 warns only about things on a list: known trackers and known-bad networks.
Many problems aren't on any list: a hidden upload, malware checking in on a timer, a
random-looking domain, or a program swapped for a different one. In the first lab run
(2026-11-21), Layer 1 caught **0 %** of those cases.

v0.3 teaches Whereabouts what each app normally does, and warns, in plain words, when the
app does something different (spec goals 2 and 4: *Detection*, *Explainability*).

**Success** (exact bar in U8 and §8):
- In the lab, Layers 1 + 2 together catch at least half of the injected cases in at least 3 of the 5
  Layer 2 scenario types (Layer 1 alone: 0 %), and
- produce **at most 1 false alarm per user per week** at medium severity or higher (spec §6.6, the
  most important trust metric).
- Every behaviour alert says why it fired, with numbers ("Uploaded 340 MB in an hour; usually about 5 MB").

## 2. Goals, non-goals, anti-goals

**Goals**
1. A saved, encrypted **behaviour profile per program file** (per full path, like the Apps screen since H2).
2. **Behaviour signals** that compare new traffic with the profile (§5), combined into one
   **explained alert** per app (§6).
3. **Feedback:** "This is fine" on a behaviour alert teaches the profile.
4. **Profile review:** see what was learned for each app, **reset** it, and mark an app as **"goes anywhere"**.
5. **Lab measurement** of Layers 1 + 2 against Layer 1, with a ship decision per signal.

**Non-goals (v0.3)**
- Layer 3 (Isolation Forest): v0.4.
- Knowing whether an app is in the foreground. The capture has no such data today (`foreground`
  exists only in `core::model`), and the service runs as SYSTEM in session 0, where it can't see the
  user's desktop. The "unusual time" signal uses hours only (§5).
- Exporting profiles, or syncing them anywhere.
- New UI screens beyond the profile view on the Apps screen.

**Anti-goals** (failure even if it "works")
- Notifications so frequent that people turn them off (more than the false-alarm target).
- **A program silencing its own monitoring**: resetting its own profile, marking itself "goes
  anywhere", or saying "this is fine" for itself. All of these go through the same trust check as
  blocking rules (`changes_something` in `service/src/server.rs`).
- **A program passing as a browser to escape destination signals.** A file named `chrome.exe`
  in a user folder must not be treated as a browser (the H2 lesson).
- The profile turning into a browsing-history log. It stores sets (each item with only its first and
  last seen times, to the millisecond) and hourly totals, never a timeline of visits, plus the
  program file's SHA-256 and signer name. Browsers' site sets are kept (U9), at registrable-domain
  level only.
- Alerts that don't say why.

## 4. The profile

**Identity:** one profile per program file, keyed by `known_app_key(path)` (lower-case full path),
the same key as `known_apps`. Flows without a known path are not profiled (they can't be told apart
from a fake with the same name). The file's latest SHA-256 and publisher are kept in the profile, so
an update to the program keeps its profile but can be noticed (§5, "binary changed").

**Contents (all in the encrypted store, schema v5):**

| Table | What | Kept |
|---|---|---|
| `profiles` | key, path, file name, first seen, `learning_until`, `learned_since` (earliest data used), last SHA-256, last publisher, `goes_anywhere` (`auto` / `user_on` / `user_off`), `reset_at` | Until the program has had no traffic for 30 days, or reset/delete |
| `profile_items` | (key, kind, value, first_seen, last_seen, how: `learned` / `allowed`), kind ∈ domain, company, country, port | An item not seen for 30 days expires (spec §6.2 sliding window) |
| `profile_hours` | (key, hour start, bytes sent, bytes received, connections), one row per active hour | 30 days |

- **Domains** are registrable domains (`example.com`). For browsers this matches what is already
  stored (spec D5).
- **Active-hours histogram** (24 buckets) and the **bytes-per-hour median and MAD** are computed from
  `profile_hours` with `core::stats` (`median`, `mad`, `robust_z`).
- **Beaconing data is never saved.** Connection start times per app and destination are kept in
  memory only, for the last few hours. *(Builder-check call:)* a beacon every 60 s usually stays one
  open flow whose `connections` count grows, so the tracker records a time whenever a flow's
  connection count goes up between ticks (2-second resolution, enough for gaps of 10 s and more). The
  destination is the registrable domain when known (beacons that rotate CDN addresses still line up),
  else the address.

**Learning period:** 7 days from the profile's **own** first data (not `known_apps.first_seen`,
which survives with history off and would make an empty profile look finished). While an app is
learning, only Layer 1 alerts apply to it, and its profile fills up. An app whose backfilled history
already spans 7 days or more is active from the upgrade (U2). *(Builder-check call.)*

**What is learned automatically, and what waits for the user** *(builder-check call)*: a finished flow
adds its destinations as `learned` **unless** they raised a medium-or-higher signal. Those are kept as
`pending`: not part of the normal profile, so an ignored warning doesn't quietly become "normal".
- *This is fine* turns pending items into `allowed`. *Block* blocks them, as today.
- While an item is pending, seeing it again **doesn't raise a new alert**: the open alert is
  updated ("seen again 5 times"). So one unanswered warning never repeats as new alerts or
  notifications and never counts twice against the false-alarm budget.
- *Dismiss* means "remind me": the item stays pending, and the next sighting after the dismiss
  raises a new alert.
- Info signals (new site) learn automatically, as they never notify.

**Expiry counts the app's active days** *(builder-check call)*: an item expires when the app has been
active on 30 days without using it, not after 30 calendar days. A tool used once a month keeps its
profile instead of coming back empty and alerting on everything. A profile whose app has had no
traffic for 180 days (the `hourly` retention) is deleted whole; if the app returns, it learns again.

**Backfill on upgrade (U2):** the schema v5 migration (or the first start after it) builds profiles
from the `flows` table (up to 30 days, has path, owner, country and port). The 180-day `hourly` table
is **not** used: it is grouped by file name, not path (a fake `chrome.exe` would be mixed in), has no
company or country, and the profile window is 30 days anyway. If history was off, there's nothing to
backfill, and apps start learning from now.

**Updates (U6):** destinations are added when the engine finishes a flow (`store_finished` in
`service/src/console.rs`, which runs whether or not history is saved): items get `last_seen` (or are
added). **Bytes are counted per hour while flows are still open** *(builder-check call)*: a flow only
finishes 5 minutes after its last traffic and carries only total bytes, so a 3-hour upload would land
in one hour. Each engine tick adds the bytes each open flow sent and received since the last tick to
its app's current hour (in memory), and the hour row in `profile_hours` is written when the hour ends
(and on shutdown). Upload spike and ratio flip are checked against the running hour on each tick, so
a big upload is caught while it happens. Backfill spreads a stored flow's bytes evenly over the hours
it spans; the lab replay does the same. Hours are local time. An in-memory cache per app avoids
reading the store on every check.

**"Goes anywhere":** `auto` means "decided by Whereabouts": on when the file name is in
`core::privacy::WEB_BROWSERS` **and** the file has a valid signature from that browser's own publisher
(e.g. Google LLC for `chrome.exe`). The user's choice (`user_on`/`user_off`) always wins over `auto`.
A file named like a browser without the right signature is treated as an ordinary app.

## 5. Signals

Starting values; every threshold is tuned in the lab (§8). "New" means "not in the profile" (neither learned nor allowed).

| Signal | Rule | Starting severity | Goes-anywhere apps |
|---|---|---|---|
| New site | registrable domain not in profile (confirmed domains only, as in Layer 1) | info | off |
| New company | owner company not in profile | medium | off |
| New country | country not in profile | medium | off |
| Upload spike | robust z of this hour's bytes sent > 6 **and** > 10 MB in the hour; needs ≥ 24 active hours in the profile | high | on |
| Ratio flip | app with ≥ 80 % download over its profile sends more than it receives in an hour, above 10 MB sent | medium | on |
| Beaconing | ≥ 6 connections to the same destination at near-even gaps (low spread of the intervals, e.g. coefficient of variation < 0.1), gaps between 10 s and 1 h, small transfers | medium | on |
| Unusual time | activity in an hour-of-day bucket holding < 1 % of the profile's active hours (no foreground data; see non-goals) | info | on |
| Random-looking name | `core::entropy` score above a threshold, not on any list, no known company | medium | on |
| Binary changed + new behaviour | SHA-256 differs from the profile's **and** the file is unsigned or its publisher changed **and** any new site/company/country signal fires | high | — (never fires: no destination signals) |

Notes:
- The thresholds for beaconing and random-looking names aren't in the spec; the values above are
  starting points for the lab.
- Severities map to the store's existing levels: spec "Low" = `info` (listed, never notified on its own).
- A signal fires at most once per app and value per day (as Layer 1 does), so a new country makes one alert, not one per connection.

## 6. Alerts

- **One behaviour alert per app per window:** signals for the same app within 10 minutes are combined
  into one alert (spec §6.4). Severity = the highest signal's, raised one level when two or more
  medium signals are combined.
- **Stored reasons:** the alert keeps its list of signals with their numbers (new column `reasons`, JSON
  in the encrypted store). Schema v5 also adds the kind `behaviour` (SQLite can't change a `CHECK`, so the
  `alerts` table is rebuilt in the migration).
- **Plain sentences in the UI**, made from the reasons, e.g.
  - "Uploaded 340 MB in an hour. Usually about 5 MB."
  - "Talked to a company it hasn't used before: Yandex (Russia)."
  - "Connected to `a8f3kq.example` every 60 seconds, 14 times."
- **Notifications:** the existing rule in `whereabouts_ipc::notify` (medium and up, at most one per app
  per hour, critical always). Info alerts are listed only.
- **Actions on a behaviour alert:** *This is fine*, *Block app*, *Block site* (when there is a site), *Dismiss*.
  - *This is fine* turns the alert's pending destinations into `allowed` (§4), so they don't alert
    again. For upload spike and ratio flip it only marks the alert seen: the hour is already in the
    profile and shapes the normal range. For **beaconing, random-looking names and unusual time** it
    saves a lasting allow for that app, signal and destination (or hour of day), in the existing
    `alert_allows` table, so a harmless app that polls every minute doesn't alert every day.
    *(Builder-check call. This saves the fact "app X polling Y is fine", not any timing data.)*
  - The 10-minute combining window updates the open alert (more reasons, higher severity if earned);
    a notification is sent at most once for it, under the existing per-app hourly limit.
  - All of these go through the existing trust check (`DismissAlert` is already in `changes_something`).

## 7. Profile review (Apps screen)

Each app card on the Apps screen gets a **Profile** section:

```
Profile                                  Learned since 2 Nov  [Reset]
Learning: 3 days left                    (or: "Active")
Sites (14)      google.com, gstatic.com, ...        last seen ...
Companies (3)   Google, Cloudflare, Akamai
Countries (4)   US, IE, NL, DE
Usually sends   about 5 MB an hour (busiest hour 40 MB)
Active hours    ▁▁▁▁▁▂▅▇▇▆▅▅▆▇▆▅▃▂▂▁▁▁▁▁
[x] Goes anywhere (recognised as a browser)
```

- **Reset** clears this app's profile and starts a new 7-day learning period. It's confirmed in a
  native Windows dialog with Cancel as the default (`win-dialog`, like "Delete everything").
- **Goes anywhere** shows whether it was recognised automatically; the user can switch it.
- Reset and goes-anywhere are new requests (`GetProfile`, `ResetProfile`, `SetGoesAnywhere`); the last
  two are added to `changes_something`, so only the app or an elevated command line can use them.
- The command line (`--profile <path>`) prints a profile for testing and the lab. It is read-only.

## 8. Lab and the ship decision

- `whereabouts-lab-replay` runs each simulated user through the shipped detector **with profiles**:
  learning weeks fill the profile, test weeks are scored (the stitching in `lab/` is already set up
  this way).
- Reports compare **Layer 1** against **Layers 1 + 2**, per signal and per scenario: detection rate,
  time to detect, false alarms per user-week at medium and up.
- **The lab needs connection times for beaconing** *(builder-check call)*: the capture export groups
  connections into flows, so real periodic traffic is invisible to the replay, and only the injected
  beacon rows have per-connection times. A false-alarm number for beaconing from that data would mean
  nothing. PR 6 adds a lab-only record of connection times (a diagnostic option of the console engine,
  not part of the user's CSV export), and the replay feeds them to the beaconing tracker. **Until the
  lab has that, beaconing ships off.** The lab timeline also keeps signature and publisher (the capture
  has them; `lab/src/wlab/sessions.py` drops them) for the "binary changed" signal.
- The 2026-11-21 run was a 3-minute smoke run. A real measurement needs longer sessions and several
  simulated users per persona; how many is the builder's call, within GitHub Actions' limits.
- **Per-signal ship decision (U4):** each signal has an on/off default in code. A signal that alone
  pushes the false-alarm rate above target ships off. The decision and its numbers go into the spec's
  implementation notes, as for v0.2.
- **Release bar (U8):** the false-alarm limit is measured with all shipped signals on **together**.
  Detection counts per scenario type; the bar is ≥ 50 % of instances in ≥ 3 of the 5 Layer 2 types.
  If no set of signals meets both, v0.3 is not released; tuning (or the signals) changes first.

## 9. Privacy and security

- P4: profiles live in the SQLCipher store. P5: profile items expire after 30 days unused; profile
  hours after 30 days; "Delete everything" clears profiles. P7: learning stays on the device.
- U1 is written on the Privacy screen ("Behaviour profiles are kept even when history is off: which
  sites, companies and countries each app uses, including your browsers, and hourly totals").
  The "delete saved history" confirm dialog says profiles are kept (U10).
- Trust: every request that changes a profile or what is alerted is limited to the app or an
  elevated command line (anti-goal 2).
- Browser recognition needs the right publisher's signature (anti-goal 3).
- Backfill and updates never read traffic content (P1): they use the same metadata as today.

## 10. Delivery (U7)

Small pull requests, in order; each with tests and a CHANGELOG line:

1. **Store:** schema v5 (profile tables, `behaviour` alerts with reasons), migration and backfill from
   `flows`, expiry in the retention run, "Delete everything".
2. **Learning:** profile updates from finished flows, learning period, in-memory cache, browser
   recognition.
3. **Signals:** in `whereabouts-detect`, as pure functions over a profile and a flow or hour, with unit
   tests per signal; beaconing tracker; the combiner.
4. **Alerts in the UI:** behaviour alerts with plain-sentence reasons; "This is fine" teaches the profile.
5. **Profile review:** IPC requests, trust checks, Apps screen section, Reset dialog, goes-anywhere,
   Privacy screen text, demo data.
6. **Lab:** replay with profiles, per-signal reports, a real-length run, threshold tuning, per-signal
   defaults.
7. **Release 0.3.0:** spec §6.2/§6.4 updated to match, README roadmap, release notes.

## 11. Left to the builder

- The wording of reasons and UI text, following the existing plain-English style.
- How many lab sessions make a real measurement.
- Whether backfill runs inside the migration or as a first-start step (it must not block the
  service from starting for long on a large history).
