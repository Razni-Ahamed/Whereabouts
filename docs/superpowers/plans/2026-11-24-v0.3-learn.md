# Whereabouts v0.3 "Learn" Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Per-app behaviour profiles (Layer 2) that warn, with reasons, when an app behaves differently from its own normal. Includes profile review and reset in the app, and lab measurement against the v0.3 release bar.

**Architecture:** The profile store lives in `whereabouts-store` (schema v5, a new `profiles.rs` module). All learning and signal logic lives in `whereabouts-detect` as a `Learner` beside the Layer 1 `Detector`. The service and the lab replay therefore run the same code. The service feeds the `Learner` from its 2-second engine tick (bytes and connection counts of open flows) and from finished flows. The IPC and the UI add behaviour alerts with reasons, plus a profile section on the Apps screen.

**Tech Stack:** Rust 2024 workspace (rusqlite/SQLCipher, serde), Tauri v2 + Svelte 5 (runes) + TypeScript (vitest), Python lab under `lab/` (uv, pytest), GitHub Actions `lab.yml`.

**Spec:** `docs/superpowers/specs/2026-11-24-v0.3-learn-design.md`. Every decision ID below (U1–U10) refers to it. Also `docs/design-spec.md` §6.2, §6.4–§6.6.

## Global Constraints

- Profile key: `whereabouts_store::known_app_key(path)`. Flows without a program path are never profiled and never get behaviour alerts.
- Learning period: 7 days from the profile's own `first_data` (not `known_apps.first_seen`).
- Item expiry: when the app has been active on 30 local days without using the item. Profile hours: kept 30 days. A whole profile is deleted after 180 days without traffic.
- Domains in profiles are registrable domains only.
- Item states: `learned`, `allowed`, `pending`. A destination that raised a medium-or-higher signal is stored `pending` and is not part of the normal profile.
- Signal starting values (§5 of the spec), as `pub const` in `crates/detect/src/signals.rs`:
  - `UPLOAD_Z = 6.0`, `UPLOAD_MIN_BYTES = 10_000_000` per hour, `UPLOAD_MIN_HOURS = 24` active hours in the profile
  - `RATIO_DOWNLOAD_SHARE = 0.8`, `RATIO_MIN_SENT = 10_000_000`
  - `BEACON_MIN = 6` connections, `BEACON_MAX_CV = 0.1`, gaps from `BEACON_MIN_GAP = 10` s to `BEACON_MAX_GAP = 3600` s, `BEACON_MAX_BYTES = 64 * 1024` per connection on average
  - `UNUSUAL_HOUR_SHARE = 0.01`
  - `RANDOM_NAME_ENTROPY = 3.5` (bits per character of the label left of the registrable suffix, length ≥ 8)
- Starting severities: new site `info`; new company `medium`; new country `medium`; upload spike `high`; ratio flip `medium`; beaconing `medium`; unusual time `info`; random-looking name `medium`; binary changed + new behaviour `high`.
- Goes-anywhere apps (effective value) get no new site, company or country signals (U5). Auto: the name is in `core::privacy::WEB_BROWSERS` **and** the signature is valid from that browser's publisher. A `user_on`/`user_off` choice always wins.
- Combining: signals for the same app within `COMBINE_WINDOW = 600` s update one open alert. Severity = the highest signal's, raised one level (capped at `high`) when ≥ 2 medium signals are combined.
- At most one alert per app, signal and value per local day. A pending item seen again updates the open alert's `seen_again` count instead of raising a new alert.
- Requests that change profiles or allows (`ResetProfile`, `SetGoesAnywhere`, `DismissAlert`) are in `changes_something` (`service/src/server.rs`). Reset is confirmed in a native `win-dialog` with Cancel as the default.
- Privacy: profiles are kept when history is off (U1) and when saved history is deleted (U10), and are cleared by "Delete everything". Beaconing timestamps are never saved.
- Release bar (U8): with all shipped signals on together, ≤ 1.0 medium-or-higher false alarms per user-week, **and** ≥ 50 % detection in ≥ 3 of the 5 Layer 2 scenario types (the lab's names: `upload`, `beacon`, `random_domain`, `swapped_binary`, `renamed_binary`). Beaconing ships off until the lab has connection times (spec §8). Expect `renamed_binary` to stay low: a renamed copy is a new path, so it gets a new profile that is still learning. That's why the bar is 3 of 5, not 5 of 5.
- Code style: follow the crate's existing style (doc comments on every pub item, `Result<_, StoreError>`, no `unwrap` outside tests, `cargo clippy --workspace --all-targets -- -D warnings` clean). UI text in the existing plain-English voice.
- Commits: one per task (more if a task says so), message style `Area: what changed`, ending with `Co-Authored-By: Claude Opus 5.5 <noreply@anthropic.com>`. Each PR adds a `CHANGELOG.md` line under `## [Unreleased]`.

## Review Focus

1. **The clock goes backwards or jumps** (manual change, sleep and resume, DST). Hour buckets and beacon gaps must never panic or count negative time. Saturating arithmetic everywhere; a sample older than the open hour goes to its own hour row. Test: `meter_survives_clock_going_back` (Task 6).
2. **A browser with thousands of sites.** Profile items per kind are capped at `MAX_ITEMS_PER_KIND = 5_000`; beyond that, the item with the oldest `last_seen` is evicted. Learner memory per app stays bounded. Test: `items_capped_per_kind` (Task 2).
3. **Upgrading a large schema-v4 (Whereabouts 0.2) database.** The migration keeps every v4 alert (kind, severity, allow key, dismissed). Backfill runs after the service has started, in batches, not inside the migration. Tests: `v4_alerts_survive_v5_migration` (Task 1), `backfill_runs_in_batches` (Task 3).
4. **Restart in the middle of an hour.** The open hour is flushed on shutdown and added (not replaced) on restart, so it is neither lost nor counted twice. Test: `flush_then_restart_adds_to_same_hour` (Task 7).
5. **Profile reset while alerts are open.** Reset deletes the profile's items and hours (pending included) and starts a new learning period. Open alerts stay listed but can no longer teach the profile: *This is fine* on them only marks them seen. Test: `this_is_fine_after_reset_only_marks_seen` (Task 9).

### Task 3: Backfill profiles from saved flows

**Files:**
- Modify: `crates/store/src/profiles.rs`
- Test: same file

**Interfaces:**
- Consumes: Task 2 types; `flows` columns (`app_path`, `app_name`, `app_sha256`, `publisher`, `domain`, `owner`, `country`, `remote_port`, `first_seen`, `last_seen`, `bytes_sent`, `bytes_received`, `connections`).
- Produces: `pub const BACKFILL_SETTING: &str = "profiles_backfilled";` and `Store::backfill_profiles(&mut self, batch: usize, local_offset_secs: i32) -> Result<BackfillProgress, StoreError>` with `pub struct BackfillProgress { pub flows_read: u64, pub done: bool }`. Each call processes up to `batch` flows after the last processed flow ID (kept in the setting as the ID; `"done"` when finished). Per flow with an `app_path`:
  - upsert the profile row (`first_data` = min, `last_data` = max, `learned_since` = earliest flow, latest SHA-256 and publisher)
  - add the domain (registrable domain as stored), company (`owner`), country and port as `learned` items
  - spread bytes and connections evenly over the UTC hours from `first_seen` to `last_seen` with `add_hours`
  - count active days by local day (`local_offset_secs`) so `active_days` and `seen_on_day` start right
- Flows without `app_path` are skipped.

### Task 6: Traffic meter and beacon tracker

**Files:**
- Create: `crates/detect/src/meter.rs`, `crates/detect/src/beacon.rs`

**Interfaces:**
- Produces (`meter.rs`):
  - `pub struct FlowSample { pub key: FlowKey, pub app_key: String, pub destination: Option<String>, pub bytes_sent: u64, pub bytes_received: u64, pub connections: u32 }`: totals of one open or just-closed flow at one tick
  - `pub struct Delta { pub app_key: String, pub destination: Option<String>, pub hour: i64, pub sent: u64, pub received: u64, pub new_connections: u32 }`
  - `pub struct Meter` with `pub fn sample(&mut self, now: SystemTime, flows: &[FlowSample]) -> Vec<Delta>`. It compares each flow with its previous totals; a flow seen for the first time counts all of its totals. Flows not in `flows` are forgotten after the call. Hours are `unix_secs / 3600`; a clock that went back puts the delta in the hour of `now`, never negative (saturating subtraction; a total that shrank counts as 0).
- Produces (`beacon.rs`):
  - `pub const BEACON_WINDOW: u64 = 4 * 3600;` `pub const MAX_TRACKED: usize = 2_000;` (app and destination pairs; least recently used evicted)
  - `pub struct BeaconTracker` with `pub fn record(&mut self, app_key: &str, destination: &str, at_secs: u64, count: u32, bytes: u64)` (count > 1 within one tick records `count` times at `at_secs`, which can't form a pattern on its own) and `pub fn check(&self, app_key: &str, destination: &str) -> Option<Reason>`. It returns `Signal::Beaconing` when, within `BEACON_WINDOW`, there are ≥ `BEACON_MIN` times whose gaps are all within `[BEACON_MIN_GAP, BEACON_MAX_GAP]`, the gaps' coefficient of variation ≤ `BEACON_MAX_CV`, and average bytes per connection ≤ `BEACON_MAX_BYTES`. `count` = connections, `observed` = the median gap in seconds.

Open-window tracking stays in memory per app; when `now - window_start < COMBINE_WINDOW`, call `update_alert`, else `add_alert`. Before raising a beaconing, random-name or unusual-time reason, check the allow key (`add_alert` already refuses allowed keys; for `update_alert` check first). One reason per app, signal and value per local day (an in-memory set, cleared at local midnight).
